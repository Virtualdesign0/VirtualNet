Roblox networking

Typed Roblox networking without the extra ceremony.

Describe a packet once, then use that same contract from the server, the client, and roblox-ts. VNet keeps the packet names, payload shape, and byte layout together, so the networking layer stays readable as the game grows.

Quick Start

Put the contract where both sides can read it.

The easiest setup is still the best one: keep one network module in ReplicatedStorage, define the packets there, and require it from both sides. The client sends intent with send; the server listens with on. 

local VNet = require(game.ReplicatedStorage.VNet)

local Net = VNet({
	BuyItem = {
		itemId = "string",
		amount = "u8",
	},

	Aim = VNet.unreliable("vec3"),

	Inventory = VNet.group({
		Equip = "string",
		Changed = VNet.t.array("string"),
	}),
})

Setup

You only need one shared network module.

There is no generator step to remember. Put the schema in shared code, give the packets you care about stable ids, and keep audit on while you are building so mistakes show up early.

01

Place the module

Put VNet somewhere both server and client scripts can require it. Most projects use ReplicatedStorage for this.

02

Write one schema

Packet names, payloads, groups, ids, and requests live in one file. That makes review and autocomplete much calmer.

03

Turn audit on

Audit catches duplicate ids, missing ids, and unsupported payload shapes before real traffic starts using them. 

-- ReplicatedStorage/Shared/Network.luau
local VNet = require(game.ReplicatedStorage.VNet)

local schema = {
	BuyItem = VNet.with({
		itemId = "string",
		amount = "u8",
	}, {
		id = 10,
	}),

	Aim = VNet.unreliable("qnormal_i16", {
		id = 11,
	}),
}

return VNet(schema, {
	audit = true,
	requireExplicitIds = true,
})

Runtime Ready

Use the ready flag as a startup guard.

When require(VNet) returns, VNet has already tried to create or find the _VNet remotes and connect the receive handlers. Check VNet.ready or VNet.isReady() before building gameplay network modules that depend on those remotes.

Simple guard

local VNet = require(game.ReplicatedStorage.VNet)

if not VNet.ready then
	error("[Game]: VNet did not finish loading.")
end

local Net = VNet({
	BuyItem = {
		itemId = "string",
		amount = "u8",
	},
})

Function form

local VNet = require(game.ReplicatedStorage.VNet)

if not VNet.isReady() then
	return
end

Net.Attack.on(function(player, data)
	Combat.handleAttack(player, data)
end)
What true means

The runtime started in a live game, the remotes are available, and the reliable and fast receive handlers are connected.

What false means

VNet was required somewhere the runtime did not start, such as a tooling script, edit-time environment, or a setup problem.

Schema

The schema is the part you come back to later.

Each key is a packet name, and each value describes what that packet carries. Use a string for a simple value, a table for an object payload, and VNet.t when the field needs bounds, precision, variants, refs, or extra rules.

Object payload

BuyItem = {
	itemId = "string",
	amount = "u8",
}

Single value

Aim = VNet.unreliable("vec3")

Grouped packets

Inventory = VNet.group({
	Equip = "string",
	Changed = VNet.t.array("string"),
})

Packet Lifecycle

One send goes through the same predictable path.

You call send; VNet checks the value, packs it, sends it, and decodes it on the other side using the same schema. That is the main point: the code you read is the contract the runtime follows.

1

Reads schema

Type strings and helpers become the packet's send plan.

2

Checks value

Wrong shapes can be rejected before they cross the network.

3

Packs bytes

Supported fields are written into a compact buffer.

4

Sends group

Same-frame packets can share one remote fire.

5

Decodes payload

The receiver gets the shape the schema promised.

Good packed shapes

Bounded numbers, vectors, colors, enums, flags, fixed tuples, delta fields, and bounded arrays.

Risky shapes

Loose tables, unbounded values, and anything that does not have a clear binary shape.

Client / Server

The client asks; the server decides.

A shared schema keeps packets clean, but it does not make the client authoritative. Let the client say what it wants to do, then check money, cooldowns, distance, ownership, and permissions on the server.

Client

Net.BuyItem.send({
	itemId = "Sword",
	amount = 1,
})

Net.Aim.send(
	workspace.CurrentCamera.CFrame.LookVector
)

Server

Net.BuyItem.on(function(player, data)
	if not Shop.canBuy(player, data.itemId) then
		return
	end

	Shop.buy(player, data.itemId, data.amount)
end)

Direction Examples

Client-to-server and server-to-client have different jobs.

Client packets usually describe intent: attack this target, buy this item, open this door. Server packets describe results: show damage, update inventory, start a round. That is why server listeners receive the player, and server sends use to, all, list, or except.

Shared schema

local Net = VNet({
	AttackRequest = {
		targetId = "u32",
		weaponId = "u16",
	},

	DamagePopup = {
		targetId = "u32",
		amount = "u16",
		critical = "bool",
	},

	MatchMessage = "string",
})

Client -> Server

Net.AttackRequest.send({
	targetId = targetId,
	weaponId = equippedWeaponId,
})

Net.DamagePopup.on(function(data)
	DamageNumbers.show(
		data.targetId,
		data.amount,
		data.critical
	)
end)

Server -> Client

Net.AttackRequest.on(function(player, data)
	if not Combat.canHit(player, data.targetId) then
		return
	end

	local amount = Combat.damage(player, data.targetId)

	Net.DamagePopup.to(player, {
		targetId = data.targetId,
		amount = amount,
		critical = false,
	})
end)

Net.MatchMessage.all("Boss spawned")
packet.to(player, payload)Send to one player.
packet.all(payload)Send to every player.
packet.list(players, payload)Send to a chosen player list.
packet.except(player, payload)Send to everyone except one player.

Security

Types keep packets honest; server code keeps the game fair.

VNet can tell whether a payload has the right shape. It cannot know whether that player is actually allowed to buy, attack, claim, trade, or move. That decision still belongs in your server code.

Validate intent

Check currency, cooldowns, distance, ownership, and permissions.

Rate limit noisy packets

Attack, cast, trade, and interact packets should have limits.

Deduplicate rewards

Use transactions when processing rewards, trades, or inventory grants.

Prefer ids for authority

Raw Instances are fine for short-lived replicated targets. For ownership, damage, rewards, and entities, prefer ids or refs.

Packet policy

local AttackRequest = VNet.packet("AttackRequest", {
	target = VNet.t.entityId,
	weaponId = "u16",
}, {
	rate = "10/s",
	burst = 3,

	validate = function(player, data)
		return Combat.canAttack(player, data.target)
	end,

	onViolation = "warn",
})

Transaction packet

ClaimReward = VNet.transaction("ClaimReward", {
	idempotencyKey = "u32",
	rewardId = "u16",
})

Net.ClaimReward.on(function(player, data)
	Rewards.claim(player, data.rewardId)
end)

roblox-ts

roblox-ts uses the same contract.

The package includes index.d.ts, so roblox-ts can read the schema and autocomplete payloads. Use VNet.client in client files and VNet.server in server files; the packet names stay the same. 

import VNet from "shared/VNet";

const schema = {
	BuyItem: {
		itemId: "string",
		amount: "u8",
	},
	Aim: VNet.unreliable("vec3"),
} as const;

const ClientNet = VNet.client(schema);
const ServerNet = VNet.server(schema);

ClientNet.BuyItem.send({
	itemId: "Sword",
	amount: 1,
});

Audit

Let audit complain before players do.

Audit is a fast sanity check for the schema. Run it while building to catch duplicate ids, missing explicit ids, invalid payloads, and shapes that cannot use the packed codec. 

local report = VNet.audit(schema, {
	requireExplicitIds = true,
})

if not report.ok then
	error(table.concat(report.errors, "\n"))
end

local Net = VNet(schema)

Pick the packet behavior at the schema.

Most packets can be plain reliable packets. Use wrappers when the packet needs a different delivery path, such as fast unreliable input, immediate one-off actions, or a thinner direct path.

Reliable

Unreliable / Fast

Aim = VNet.fast("vec3")

Instant

Parry = VNet.instant({
	targetId = "u32",
	startedAt = "f64",
})

Direct

InputTick = VNet.direct({
	seq = "u32",
	buttons = "u8",

Options

Hit = VNet.with({
	targetId = "u32",
	damage = "u16",

Packet Methods

Most gameplay code only needs these calls.

After the schema is built, packets behave like small typed channels. Send one payload, listen for one payload, or group many same-frame payloads when a system is noisy.

send(payload)Send one payload.
on(listener)Listen for that packet.
many(payloads)Queue several payloads for the next flush.
flushMany(payloads)Send a batch right now.
onBatch(listener)Read a batch in one callback.
to / all / list / exceptPick which players receive a server packet.
Net.Inventory.Changed.onBatch(function(player, payloads, count)
	for index = 1, count do
		print(player.Name, payloads[index])
	end
end)

Local Packets

Local code can use the same packet style.

Some messages should never cross the network: UI events, local controller messages, prediction feedback, and test hooks. Bindable packets keep those local flows shaped like the rest of the network.

		Net.Attack.reject(player, {

VNet.t

Start simple, then add stricter types where they matter.

Most fields can be simple strings like "u8", "string", or "vec3". Reach for VNet.t when you want bounds, arrays, maps, optional fields, variants, refs, or custom precision.

Dynamic types

Profile = {
	name = VNet.t.string(3, 20),
	recentItems = VNet.t.array("u32", 0, 32),
	currencies = VNet.t.map("string", "u32"),
}

Variants and flags

Action = VNet.t.variant({
	Move = { x = "i16", z = "i16" },
	Attack = { targetId = "u32" },
})

StateFlags = VNet.t.flags({
	"Running",
	"Blocking",
	"Stunned",
})

U4

Two tiny numbers can share one byte.

Use U4 when each value fits between 0 and 15, such as a small mode id or slot index. The first value uses the low 4 bits, and the second value uses the high 4 bits.

low 4 bits high 4 bits 
NibblePair = "U4"

Net.NibblePair.send({ 3, 12 })
-- byte = 3 + 12 * 16
-- byte = 195 / 0xC3
Boolean1

Eight yes/no flags in one byte.

Use Boolean1 for input or state flags. It is not a single boolean value; the payload is a list of eight booleans packed into one byte.

1 2 3 4 5 6 7 8 
InputFlags = "Boolean1"

Net.InputFlags.send({
	true, false, true, false,
	false, false, false, true,
})
-- bits 1, 3, and 8 are on
-- byte = 1 + 4 + 128 = 133
Boolean8

One normal boolean when clarity matters.

Use Boolean8 when the field is simply true or false. Use Boolean1 only when you intentionally want eight flags packed together.

0x00 false 0x01 true 
IsBlocking = "Boolean8"

Net.IsBlocking.send(true)
-- true  -> 1 byte: 0x01
-- false -> 1 byte: 0x00

Requests

Use requests when the caller needs a reply.

Requests are for question-and-answer flows: load a profile, ask for a store result, or fetch a small server decision. They are easier to read than pairing one request packet with one response packet by hand.

Define

GetProfile = VNet.request({
	input = { userId = "u32" },
	output = { level = "u16", coins = "u32" },
	requestId = 100,
	responseId = 101,
})

Handle / invoke

Net.GetProfile:handle(function(player, data)
	return { level = 20, coins = 5000 }
end)

local ok, profile = Net.GetProfile:invoke({
	userId = player.UserId,
}, { timeout = 5 })

Delta / Sync

Send only the fields that changed.

Delta is useful when the client already has a base copy of an entity. Instead of resending the whole state every time, the server sends the few fields that changed and the client merges them into its local table.

Schema

local Net = VNet({
	EntityState = VNet.delta({
		health = "u16",
		shield = "u16",
		position = "qvec3_i16",
	}),
})

Server sends changes

local function damageEntity(entityId, amount)
	local state = EntityStore[entityId]

	state.health = math.max(0, state.health - amount)

	Net.EntityState.sendDelta(entityId, {
		health = state.health,
	})
end

Net.EntityState.toDelta(player, entityId, {
	health = 80,
	shield = 20,
})

Client merges changes

local entities = {}

Net.EntityState.onDelta(function(entityId, changes)
	local state = entities[entityId]

	if not state then
		state = {}
		entities[entityId] = state
	end

	for name, value in pairs(changes) do
		state[name] = value
	end

	EntityVisuals.update(entityId, state)
end)

Targeting delta packets

Net.EntityState.allDelta(entityId, {
	position = newPosition,
})

Net.EntityState.listDelta(players, entityId, {
	shield = 50,
})

Net.EntityState.exceptDelta(owner, entityId, {
	health = 0,
})

What JoinSync solves

A late player did not see the packets that built the current match. JoinSync lets the server replay the important pieces in an order you choose: match data first, teams next, entities after that, then inventory or effects.

What the marker means

Each stage handler sends normal VNet packets. VNet flushes those packets, then sends a small reliable marker. When the client sees onStage(stage), the packets for that stage were sent before the marker.

Client waits for ready

	"MatchState",
	"Teams",
	"Entities",
	"Inventory",
}, {
	name = "Match.Join",
})

MatchJoin.onStage(function(stage)
	LoadingScreen.setStep(stage)
end)

MatchJoin.onDone(function()
	LoadingScreen.hide()
	Gameplay.start()
end)

Blocking wait

if not MatchJoin.isDone() then
	LoadingScreen.show()
	MatchJoin.wait()
end

LoadingScreen.hide()
Gameplay.start()

-- Before another match loading flow:
MatchJoin.reset()
Method Meaning
define(stages, options)

Creates the same named pipeline on server and client. Use a name when you want the connection to be obvious.

start(player, handlers)

Server only. Runs handlers in stage order. A missing handler is okay; VNet still sends that stage marker.

onStage(stage)

Client side. Fires when a stage marker arrives, useful for loading text, progress bars, or enabling one system at a time.

onDone() / wait()

Fires or resumes after the final marker. Start gameplay, hide the loading screen, or allow input here.

Instances / Refs

Choose the target type by what the object really is.

Direct Instances, Players, characters, and registry refs all look similar in code, but they solve different problems. A direct Instance uses Roblox's normal RemoteEvent behavior. A registry ref sends your own small id, then the receiver resolves that id from its local registry.

Direct replicated Instance

If Roblox already replicates the object to the receiver, VNet.t.instance() is the straightforward choice. It sends the Instance through RemoteEvent normally; it is not a compact id codec.

Player characters

If you mean a player's current character model, use VNet.t.character(). VNet resolves it through the player's UserId, so you do not need a custom registry id.

NPCs, custom entities

Use VNet.t.ref("Character") or another kind when the target belongs to your own entity system. Register when it spawns, and clean it up when it despawns.

Type Use it when
VNet.t.instance(className?)

You want to pass a Roblox Instance directly. Use "BasePart", "Model", "Tool", "ProximityPrompt", or any other Roblox class name to restrict it with IsA. Leave it empty to accept any replicated Instance.

VNet.t.player()

You want to send a Player. VNet writes the player's UserId and resolves it with Players:GetPlayerByUserId on the receiver.

VNet.t.character()

You want to send a player's current character model. VNet writes the owning player's UserId, then reads player.Character on the receiver.

VNet.t.ref("Character")

You want to send a model from your own registry, such as an NPC, summon, tool, hitbox, or custom entity. You choose the id and register it on both sides.

Easy rule

Already replicated object? Use instance(className): instance("Model"), instance("BasePart"), or instance() for any Instance. Player object? Use player(). Player's current character? Use character(). Anything you spawned, tracked, and identified yourself? Use ref(kind).

Important edge cases

instance() only works when the receiver already has that Instance replicated. character() can fail if the player has no current character on the receiver.

Track player characters

local Players = game:GetService("Players")
local cleaners = {}

local function clearCharacter(player)
	local cleanup = cleaners[player]

	if cleanup then
		cleanup()
		cleaners[player] = nil
	end
end

local function trackPlayer(player)
	local function registerCharacter(character)
		clearCharacter(player)

		cleaners[player] = VNet.Registry.register(
			"Character",
			character,
			player.UserId
		)
	end

	player.CharacterAdded:Connect(registerCharacter)
	player.CharacterRemoving:Connect(function()
		clearCharacter(player)
	end)

	if player.Character then
		registerCharacter(player.Character)
	end
end

Players.PlayerAdded:Connect(trackPlayer)
Players.PlayerRemoving:Connect(clearCharacter)

for _, player in ipairs(Players:GetPlayers()) do
	trackPlayer(player)
end

Track NPC entities

local function spawnNpc(entityId, model)
	local cleanup = VNet.Registry.register(
		"Character",
		model,
		entityId
	)

	model.Destroying:Once(cleanup)

	Net.NpcSpawn.all({
		id = entityId,
		template = model.Name,
	})
end

Net.HitConfirm.on(function(player, data)
	-- data.target is the registered Model
	print(data.target.Name, data.damage)
end)
Rule Why
Register before use

If a packet arrives before the receiver knows the id, decode fails and the packet is dropped.

Clean both sides

Cleanup is local. The server cleaning an id does not automatically clean the client registry.

Reuse stable ids carefully

For player respawns, reuse UserId. For NPCs, reuse an entity id only after the old model is fully despawned.

Bindable Transport

Use bindable packets for messages inside one runtime.

VNet.bindable uses the same packet shape without crossing the Roblox network. It is for modules inside the same client or the same server that need to talk cleanly without creating their own BindableEvent layer.

Good places to use it

UI events, local controllers, server-side services, test harnesses, and module-to-module messages that should stay local.

Not for networking

Bindable packets do not go from client to server. When data needs to cross that boundary, use normal VNet packets.

Define local packets

local UIEvents = VNet.bindable({
	MenuOpened = {
		menuId = "string",
		source = "string",
	},

	Toast = {
		text = VNet.t.string(1, 80),
		kind = VNet.t.enum({ "Info", "Error" }),
	},
})

Send from one module

local InventoryButton = {}

function InventoryButton.clicked()
	UIEvents.MenuOpened.send({
		menuId = "Inventory",
		source = "Hotbar",
	})
end

return InventoryButton

Listen from another module

UIEvents.MenuOpened.on(function(data)
	MenuController.open(data.menuId)
	Analytics.track("menu_opened", data.source)
end)

UIEvents.Toast.on(function(data)
	ToastController.show(data.text, data.kind)
end)

on(listener)Listen from another local module.
once(listener)Listen once, then disconnect.
wait()Yield until the next local payload arrives.
many(payloads)Send several local payloads.

Shard Bridge

Use Shard when another server needs to hear about it.

Shard is the server-to-server side of VNet, built on MessagingService. Use it for party, lobby, match, trade, reward, or queue flows where one server needs to tell another server what happened.

What it does

Validates the payload against a schema, publishes it to a MessagingService topic, and lets matching servers listen by packet name instead of parsing loose message tables.

What it is not

It is not for high-frequency gameplay replication. Keep movement, combat effects, and normal client traffic on regular VNet packets.

Shared shard schema

local PartyShardSchema = {
	InviteAccepted = {
		partyId = "u32",
		userId = VNet.t.playerId,
		matchId = "string",
	},

	TradeLocked = {
		tradeId = "u32",
		fromUserId = VNet.t.playerId,
		toUserId = VNet.t.playerId,
	},
}

Lobby server sends

local PartyBridge = VNet.Shard.bridge(
	"Party",
	PartyShardSchema,
	{
		shardId = "lobby",
		dedupe = true,
	}
)

PartyBridge:Send("InviteAccepted", {
	partyId = 42,
	userId = player.UserId,
	matchId = "match-17",
}, "match-17")

Match server receives

local PartyBridge = VNet.Shard.bridge(
	"Party",
	PartyShardSchema,
	{
		shardId = "match-17",
		dedupe = true,
	}
)

PartyBridge:On("InviteAccepted", function(data, source)
	PartyService.addPlayer(
		data.partyId,
		data.userId,
		source
	)
end)

Manual start / stop

local Bridge = VNet.shard("Trade", TradeSchema, {
	shardId = "trade",
	autoStart = false,
	validate = true,
})

Bridge:On("TradeLocked", function(data)
	TradeService.applyLock(data.tradeId)
end)

Bridge:Start()

game:BindToClose(function()
	Bridge:Stop()
end)
Option Meaning
topic

Custom MessagingService topic. By default VNet uses VNet.Shard.<name>.

shardId

The local server role or id. A message with a target only runs on bridges whose shardId matches that target.

dedupe

Uses MemoryStore to skip duplicate message ids for the dedupe TTL. Useful for trade, rewards, party, and queue messages.

echo

Defaults to false, so a server ignores its own published messages. Set true only when local echo is useful.

Troubleshooting

When something feels wrong, start here.

Symptom What to check
Listener never fires

Make sure both sides require the same network module and that the packet is in the group you think it is.

Audit fails

Check duplicate ids, missing explicit ids, unsupported payloads, and dynamic values without bounds.

Request times out

Make sure the server registered handle, the ids are unique, and the handler returns before the timeout.

Map shape is confusing

VNet maps are plain Luau tables. In roblox-ts, treat them like dictionaries instead of JavaScript Map objects.

Prediction needs rollback

Use predict for local feedback and reject when the server needs to undo it.

One network fire per call is useful for timing, not noisy state.

The useful part here is not only bytes per message. Normal VNet packs many same-frame sends into one receive path, so the server does far fewer callbacks. That is usually the better shape for movement, entity state, aim, effects, inventory deltas, and other noisy updates.

Normal VNet

packet.send writes into the frame queue. VNet then sends one packed group for many same-frame messages.

VNetImmediate

VNet.instant(...) skips the frame queue and sends a single packet now. It saves the frame wait, but pays one network fire and one receive callback for every call.

VNetDirect

VNet.direct(...) keeps the frame queue by default, but skips VNet-side prediction, middleware, validation, policy, transaction, and early queue work. It is the thinner VNet path for packets that do not need those features.

Immediate is about timing, not throughput. Use it for parries, purchases, trade confirms, reward claims, and small request-like actions where the packet should leave right away. Avoid it for movement, aim, entity snapshots, and other state that fires every frame.

Direct is for packets where you intentionally want less VNet-side work. It still batches same-frame traffic unless you pass { immediate = true }. If the packet needs validation, policy checks, idempotency, or prediction hooks, use normal VNet or VNet.instant(...) instead.

Runtime Shape

VNet creates a small remote folder.

In a running place, VNet keeps the network surface small: one folder and two remotes, one reliable and one fast. Your packet names and ids live in the schema, not as a pile of generated RemoteEvents.
